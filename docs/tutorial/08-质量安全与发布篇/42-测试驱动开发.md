# 第 42 章：测试驱动开发

## 本章目标

掌握红、绿、重构循环，区分纯函数、组件、服务边界、Rust 单元和端到端测试，并能为真实修改选择成本最低且有效的测试。

## 开始前需要会什么

能运行 Vitest 与 Cargo test，理解断言、依赖注入和纯函数。

## 新术语表

| 术语 | 含义 |
|---|---|
| RED | 新测试因缺少目标行为而正确失败 |
| GREEN | 用最小实现让测试通过 |
| Refactor | 行为不变时改善结构 |
| Regression | 曾正常的行为再次坏掉 |
| Test double | fake、stub、mock 等替身 |
| Contract test | 验证边界双方共同约定 |

## 先建立直觉

测试驱动不是先写一大堆测试，而是先把下一小步的可观察结果说清楚。失败必须与目标一致：若测试因语法错误失败，还没有得到有效 RED。

## 图解

~~~mermaid
flowchart LR
  A[写一个行为测试] --> B[确认因缺少功能失败]
  B --> C[最小实现]
  C --> D[测试通过]
  D --> E[重构]
  E --> D
  D --> F[下一小步]
  F --> A
~~~

## 跟我一步一步做

1. 把需求改成用户可观察行为，例如“休息十分钟后有效学习时间不增加”。
2. 选择最低测试层：时间计算先测纯函数，不先渲染整页。
3. 写测试并运行，确认失败原因正是目标能力缺失。
4. 只实现让当前测试通过所需的最小行为。
5. 运行相关测试，再运行受影响模块。
6. 通过后重构重复代码；每次小改继续验证。
7. 跨前后端分别写服务 contract 与 Rust command/仓储测试。
8. 修 bug 时先写能重现症状的测试，确认旧代码失败。
9. 文件和数据库测试使用临时目录或内存库，不碰真实数据。
10. 最后运行完整测试与生产构建。

## 完整示例

~~~ts
it("does not count break time", () => {
  const started = startSession("数学", 0);
  const resting = startBreak(started, 60_000);
  expect(elapsedWorkMs(resting, 660_000)).toBe(60_000);
});
~~~

测试不等待十分钟，而是注入时间戳，所以快速、稳定、可重复。

## 逐段解释

纯函数测试适合排序、校验、统计和状态机；组件测试验证用户输入、按钮和可访问名称；服务测试固定 command 名、参数包和错误转换；Rust 测试保护数据库、文件和安全边界；少量集成测试确认路由与组合。

mock 越多，测试越可能只证明 mock 会按预设工作。优先 fake 和真实纯逻辑，只在外部网络、系统弹窗或 invoke 边界使用 mock。

## 运行并观察

依次运行一个测试文件、教学应用测试、完整前端测试和 Cargo 测试。故意改坏一个预期，阅读 expected、received 和调用位置，再恢复。观察异步测试为何可能单独通过、全量超时。

## 常见错误与修复

- 测试先因语法失败：先修测试，再确认行为 RED。
- 只测内部变量：断言用户可见结果或公开接口。
- 所有依赖都 mock：保留真实纯函数和 fake 服务。
- 为截图像素写脆弱断言：结构测试和视觉检查分工。
- 局部通过就宣布完成：还要完整测试、build 和静态检查。
- 偶发失败只靠重跑：记录频率并隔离根因。

## 必做练习

为恢复资料完成一次红绿重构；为一个错误先写回归测试；把一个过度 mock 的测试改成 fake；解释测试通过为何不等于绝对正确。

## 选做挑战

为每个模块列出纯函数、组件、服务、Rust 和真机验收各一项，并删掉重复且不增加信心的测试。

## 答案与思路

恢复测试先准备 deletedAt 非空记录，再断言恢复后为空且 version 增加。测试只能覆盖已写场景，不能替代可用性、安全审查与真实设备验证。
