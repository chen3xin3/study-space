# 第 48 章：怎样独立查资料和解决问题

## 本章目标

学会把报错变成可搜索问题，优先使用官方与一手资料，建立最小实验，验证答案适用于当前版本，并沉淀自己的解决记录。

## 开始前需要会什么

能稳定重现问题、阅读堆栈、识别项目技术栈与版本。

## 新术语表

| 术语 | 含义 |
|---|---|
| Primary source | 官方文档、源码、标准或原始论文 |
| Minimal reproduction | 只保留问题所需内容的小项目 |
| Version context | 框架、平台和依赖的具体版本 |
| Search query | 用于检索的错误片段与环境关键词 |
| Verification | 用测试和实验确认答案 |
| Workaround | 暂时绕过问题的方法，不一定解决根因 |

## 先建立直觉

查资料不是把整段错误丢给搜索引擎然后复制第一段代码。你需要先知道自己在问什么，再判断答案针对哪个版本、解决的是根因还是表面症状。

## 图解

~~~mermaid
flowchart TD
  A[错误与目标] --> B[提取稳定关键词]
  B --> C[官方文档/源码/Issue]
  C --> D[核对版本与平台]
  D --> E[最小实验]
  E -->|不成立| B
  E -->|成立| F[加入项目回归测试]
  F --> G[记录原因与来源]
~~~

## 跟我一步一步做

1. 先写期望、实际、环境、版本和最短重现步骤。
2. 从报错中保留错误码、关键函数和第一条项目相关信息，删除个人路径与敏感内容。
3. 搜索时加入技术、版本与平台，例如 Tauri 2 Android content URI。
4. 技术问题优先查官方文档、官方仓库源码、发布说明和维护者 issue。
5. 确认文档属于当前主版本；旧版 API 名可能相同但行为不同。
6. 阅读完整上下文，不只复制代码块；注意前置条件、安全警告和平台限制。
7. 在独立小项目或测试中验证，不先改真实数据库和用户文件。
8. 若多个答案冲突，比较发布日期、版本、作者权威性和可复现实验。
9. 将有效结论转成回归测试或检查脚本。
10. 记录问题、根因、无效尝试、有效方案、来源和验证命令。
11. 使用 AI 时要求它说明假设和验证方法，不把输出当权威来源。
12. 高风险的安全、加密、医疗、法律或付费 API 问题必须查最新一手资料。

## 完整示例

问题：Android 选择照片后重启无法显示。

调查路线：确认保存的是 content URI → 查询 Android/Tauri 当前版本文件访问文档 → 建最小选择器实验 → 验证 URI 权限是临时的 → 结论是导入时复制字节到应用受管目录 → 为重启后读取写测试 → 在真实平板验证。

## 逐段解释

错误原文很重要，但搜索前应移除用户名、密钥和私人路径。版本上下文能过滤大量无关答案。Stack Overflow 或博客可以提供方向，最终要用当前版本文档、源码或实验确认。

最小复现同时帮助你理解与求助：别人不需要运行整个学习空间，也能看见问题。若最小项目正常，原因多半在项目组合、配置或共享状态。

## 运行并观察

挑一个真实构建警告，记录依赖版本，用精确错误搜索官方来源；在不改生产代码的情况下做最小验证。随后写一页问题记录，并在几天后只看记录重复解决。

## 常见错误与修复

- 搜索“软件打不开”：加入准确错误码、版本和平台。
- 复制旧版答案：核对发布日期和主版本。
- 第一条结果就修改生产代码：先做最小实验。
- 只看成功案例：同时搜索限制、bug 和 breaking changes。
- 把 workaround 当根因修复：明确标记临时性。
- 搜索内容带密钥或私人路径：先脱敏。

## 在“学习空间”项目里找到它

使用 [package.json](../../../package.json)、[Cargo.toml](../../../src-tauri/Cargo.toml)、[Tauri 配置](../../../src-tauri/tauri.conf.json) 确认版本上下文；用 [诊断服务](../../../src/services/diagnostics/diagnostics.service.ts) 收集脱敏事实；将结论写进对应测试或 docs。

## 必做练习

把一个模糊问题改写成精确查询；为同一问题比较官方文档、博客和论坛；建立最小复现；写出验证结论和回归测试；制作个人问题记录模板。

## 选做挑战

选择一个依赖升级，阅读发布说明和迁移指南，列出破坏性变更，先在隔离分支运行测试与构建，再决定是否升级，不把升级和业务功能混在一个提交。

## 答案与思路

精确查询至少包含错误、技术、版本和平台。一手资料决定 API 事实，社区资料提供经验，实验决定当前环境是否成立。记录必须能让未来的你复现，而不是只写“已解决”。
