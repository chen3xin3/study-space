# 第 46 章：从需求到实现计划

## 本章目标

把模糊想法转成范围明确、风险可控、可测试、可逐步交付的实现计划，并学会保护已有未提交修改。

## 开始前需要会什么

已完成至少一个前后端功能，能读路由、服务、command、仓储和测试。

## 新术语表

| 术语 | 含义 |
|---|---|
| Requirement | 用户真正要达到的结果 |
| Acceptance criteria | 判断是否完成的可验证条件 |
| Scope | 本次包含与不包含的范围 |
| Dependency | 必须先完成的工作 |
| Risk | 可能导致失败或数据损失的因素 |
| Milestone | 可以独立验证的阶段结果 |
| Rollback plan | 失败时怎样回到安全状态 |

## 先建立直觉

“做一个 AI 整理功能”不是计划。计划要回答：用户选择哪些资料、AI 返回什么、谁确认、保存到哪里、失败时保留什么、怎样验证没有泄密。

## 图解

~~~mermaid
flowchart TD
  A[用户问题] --> B[目标与非目标]
  B --> C[调查现有实现]
  C --> D[业务流程与数据流]
  D --> E[风险和边界]
  E --> F[可验证任务]
  F --> G[按依赖排序]
  G --> H[实施与检查点]
  H --> I[验收]
~~~

## 跟我一步一步做

1. 用一句话写用户结果，不写技术方案。例如“能从英语试卷照片中保存原图并整理成可搜索资料”。
2. 写非目标，例如第一版不自动裁题、不删除原图、不做云同步。
3. 调查当前代码：入口路由、页面、服务接口、command、数据库表、附件与现有测试。
4. 画成功流程和三条失败流程。
5. 列出数据字段、状态转换和跨平台差异。
6. 写验收条件，使用“给定、当、那么”描述可观察结果。
7. 识别高风险项：数据库迁移、文件删除、密钥、网络、并发、旧数据升级和真机权限。
8. 把工作拆成小任务：测试 → 最小实现 → 局部验证 → 提交。
9. 按依赖排序；数据模型和服务合同通常早于复杂页面。
10. 每个任务写准确文件、命令、预期失败和预期通过结果。
11. 开始前检查 git status；工作区脏时保留用户修改，必要时使用隔离 worktree。
12. 设置检查点，不要等全部完成才运行构建。

## 完整示例

需求“给资料加入收藏”可拆为：

1. 明确 active/trash 中都能否收藏；
2. 纯函数测试：切换收藏不修改旧对象且 version+1；
3. 服务 contract：update 接受 id、version、favorite；
4. Rust 仓储测试：旧 version 被拒绝；
5. 页面测试：按钮名称、保存中、冲突提示；
6. 实现领域、服务、后端、页面；
7. 局部测试、完整测试、构建和手动平板检查；
8. 验收：重开后收藏仍在，冲突不静默覆盖。

## 逐段解释

好计划描述行为和边界，但不过早规定每一行代码。调查先于设计，避免重做已有服务。任务粒度以“可以写一个失败测试并独立提交”为宜。

计划不是承诺永不变化。新证据出现时更新计划并说明原因，但不能悄悄扩大范围。

## 运行并观察

选择一个小需求，不改代码，先在临时文档写目标、非目标、流程、风险、文件图和验收。随后用本章的计划检查表逐项复核，找出自己遗漏的失败路径。

## 常见错误与修复

- 需求直接翻译成组件名：先写用户结果。
- 未调查现有代码就规划：先搜索入口与服务。
- 任务写“完成后端”：拆到具体行为和测试。
- 没有非目标：范围会无限增长。
- 只写成功流程：补断网、冲突、取消和重启。
- 脏工作区直接 reset：保留修改并隔离工作。

## 必做练习

为“试卷资料库”写目标与非目标；列十条验收条件；画成功和失败数据流；拆成六个可测试提交；写出如何保护当前未提交修改。

## 选做挑战

选一个涉及 Windows 与 Android 的功能，加入平台能力表、权限表、旧数据升级、回滚方案和真机验收矩阵。

## 答案与思路

第一版重点是原图、分类、日期、搜索和关联，不急于自动切题。验收应覆盖保存、重开、筛选、删除恢复、错误和触控。隔离工作可使用新 worktree，但不要自动把脏目录修改复制或覆盖。
